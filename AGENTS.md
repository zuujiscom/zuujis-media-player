# Zuujis Media Player — Agent Guide

## Project at a glance

The app is called **Zuujis Media Player** (the product, `Zuujis Media Player.app`, and every user-visible string). The Xcode project, target, scheme and source folder are `ZuujisMediaPlayer`, the bundle ID is `com.zuujis.MediaPlayer`, and data lives in `~/Library/Application Support/Zuujis Media Player/`. Before the rename these were `AudioEqualizer` / `com.zuujis.AudioEqualizer`; `Models/AppPaths.swift` copies the old Application Support folder and preferences across once at launch and leaves the originals for the old app. macOS asks for the audio-capture permission again once, because it is tied to the bundle ID. `ZuujisMediaPlayer` is a native SwiftUI macOS app that applies a system-wide graphic EQ and master gain to the Mac's current default output. It targets macOS 26.0 and relies on macOS process-tap APIs, AVFoundation, CoreAudio, and Accelerate/vDSP. There are no package dependencies. Unit tests for the pure logic live in a separate Swift package, `Tests/` (see Validation).

Open `ZuujisMediaPlayer.xcodeproj` in Xcode and build the `ZuujisMediaPlayer` scheme. A command-line build can use:

```sh
xcodebuild -project ZuujisMediaPlayer.xcodeproj -scheme ZuujisMediaPlayer -configuration Debug -derivedDataPath /tmp/ZuujisMediaPlayer-derived build
```

Do not lower the deployment target without replacing or conditionally compiling the macOS 15+/26 SDK process-tap APIs (`CATapDescription`, `AudioHardwareTap`, and `AudioHardwareAggregateDevice`).

## Architecture

- `ZuujisMediaPlayer/App/ZuujisMediaPlayerApp.swift`: app entry point. Creates and injects one `AudioEngine`, `MeterState`, and `PresetManager`.
- `ZuujisMediaPlayer/Audio/AudioEngine.swift`: the central audio lifecycle, Core Audio device monitoring, EQ state, route creation, manual AVAudioEngine rendering, realtime renderer, and metering state.
- `ZuujisMediaPlayer/Audio/SpectrumAnalyzer.swift`: reusable 2,048-sample FFT and RMS helpers. It returns 64 normalized spectrum bins, spaced logarithmically from 20 Hz to min(20 kHz, Nyquist) and rebuilt whenever the tap's sample rate changes. `SystemAudioRenderer.analysisWindow` must match the FFT size or the tail of each window is zero-padding.
- `ZuujisMediaPlayer/Audio/PlayerEngine.swift` + `Views/PlayerView.swift`: the file player (FLAC, ALAC, WAV, AIFF, MP3, AAC via `AVAudioFile`; no FFmpeg). It is a **second, separate audio path** — its own `AVAudioEngine` (`AVAudioPlayerNode → EQ (`GraphicEQ`) → limiter → mainMixer → default output`) that never touches the process tap or aggregate device. The tap excludes this process on purpose, so the player's output is not captured and the player applies the EQ itself, mirroring `AudioEngine.bands`, `isBypassed`, `masterGain` and `isRunning` onto its own node (engine off = every band bypassed and gain 0: the power button is the EQ's master switch for the player too) through the same `EQResponse.compensated` mapping. Do not route player audio through the system route, and do not create a tap for it.
- `ZuujisMediaPlayer/ViewModels/PlaybackQueue.swift` is the playlist: items, play order (list order or one fixed shuffle permutation), repeat mode, current item, folder scan, tag/duration loading (four files at a time, applied to `items` in batches of 40; songs the library knows are filled from `knownMetadata`, set in `bootstrap()`, and never read from disk, because playing a library song queues the whole list and re-reading a thousand files held the CPU at 25-50% for seconds) and persistence to Application Support `queue.json`. It knows nothing about audio — `PlayerEngine` asks `itemAfterCurrent()` (what ends-on-its-own goes to; honours repeat-one) or `itemForSkipForward()`/`itemForSkipBack()` (Next/Previous; repeat-one does not trap them) and reports back with `setCurrent`. `Views/PlaylistView.swift` is its window.
- **Gapless.** While a track plays, the next is already scheduled on the same `AVAudioPlayerNode`, so the join is sample-exact. Each scheduled stretch is a `Segment` with a `startSample` on the node's own, never-resetting timeline; position is found by matching the node's `sampleTime` against the segments, never by trusting callback timing. Only a next file with the graph's sample rate **and** channel count can join; otherwise `scheduleNext` records it in `unschedulableNext` and the graph is rebuilt when the track ends (a short gap). `scheduledTrackCount` of 2 means a next track is queued behind the playing one. Editing the queue goes through `reconcileWithQueue()`, which re-schedules from the current frame only when what is queued no longer matches (a brief gap, edits only); `unschedulableNext` stops it retrying a track that can never join on every tag update.
- Player rules learned the hard way: a segment's completion handler also fires when the node is stopped for a seek, so every schedule/stop/rebuild bumps `session` and a handler only counts if its token is still current (otherwise each seek reads as "track ended"). The EQ node takes any band count, so a band-count change needs no rebuild; `AVAudioEngineConfigurationChange` (output device switch) rebuilds the graph on a fresh engine and resumes at the same frame. `removeTap` throws an ObjC exception on a node not attached to an engine — go through `removeMeterTap()`. The position is polled via `currentTime()`, not published. FLAC and ALAC carry their source bit depth in `mFormatFlags` (1/2/3/4 = 16/20/24/32 bit), not `mBitsPerChannel`. An unreadable file is skipped (at most once round the queue). `PlaybackQueue` must not import SwiftUI-only conveniences such as `move(fromOffsets:)` — the model layer stays buildable without SwiftUI.
- **Playlists.** `Models/Playlist.swift` (pure: add without duplicates, remove, move, nudge, `uniqueName`) and `ViewModels/PlaylistStore.swift` (persisted to Application Support `playlists.json`, injected as an environment object into the main window *and* the Queue window). **Favorites** is an ordinary `Playlist` with the fixed id `PlaylistStore.favoritesID`, created at init if missing, sorted first, and protected from rename/delete in the store; `favoritePaths` is the cached set behind every heart (`isFavorite`, `toggleFavorite`). Playlists hold file *paths*, not library tracks, so they survive rescans and offline drives; the UI resolves paths against the library (`byPath`). Dragging a song uses the payload `"zuujistrack:"+path` (`LibraryView.dragPrefix`). The old play list window is now the **Queue** (`PlaylistView`, `PlaybackQueue`) — "playlist" in the UI means a saved one. `NamePrompt`/`NameSheet` (in `LibraryView.swift`) are the shared one-line prompt.
- **Library.** `Models/LibraryModel.swift` is pure grouping/sorting/tag-parsing (`LibraryTrack`, `LibraryModel`, `TagEdit`, `FLACTags`); `ViewModels/LibraryStore.swift` owns folders and tracks and persists them to Application Support `library.json`; `Views/LibraryView.swift` is the card (plus the `EditTagsSheet`). The card has three browse modes (`artists`/`genres`/`playlists`, `@AppStorage("libraryBrowse")`); Genres filters the same artist/album/song columns through `LibraryModel.songs(_:inGenre:)`. Song rows keep a multi-selection (`selection`/`anchor`, `click(_:in:)` reads ⌘/⇧ from `NSEvent.modifierFlags`; `songTargets(for:)` is what a right-click acts on). `Saved.schema` in `library.json` is bumped when a new tag is added: an older file gets every track's size set to -1 so the next scan re-reads tags once (schema 3: MP3 years come from the ID3 TYER/TDRC frames, since the common creation date is often empty). **FLAC files with an ID3v2 tag glued in front** (some rips) are not valid FLAC: `FLACTags.read` skips the prefix, and `TagWriter` converts it to Vorbis comments (`ID3Prefix`) and drops it on the next write, always as a full rewrite. Scans are incremental: a file's tags are re-read only when its size or mtime differs from the cached track, four reads at a time, published in batches of 40. A folder that is missing is *offline*, not empty — its tracks are kept. Compare paths with `LibraryStore.folder(_:contains:)`, which ignores a leading `/private` (enumeration reports `/private/var` for `/var`). AVFoundation ignores FLAC Vorbis comments, so `FLACTags` walks the metadata blocks and reads only VORBIS_COMMENT (never PICTURE); `TrackMetadata` (in `PlaybackQueue.swift`) prefers ALBUMARTIST over ARTIST so compilations stay on one album. A leading number in a file name is a track number only if a separator follows ("7 Seconds" is a title).
- **Tag edits.** A `TagEdit` is a partial change (nil field = untouched, "" or 0 = cleared). `LibraryStore.apply(_:to:writeToFiles:)` updates the library at once and keeps the merged edit in `edits` (persisted, re-applied after rescans). With `writeToFiles`, `Models/TagWriter.swift` writes FLAC (Vorbis comments) and MP3 (ID3v2.3/2.4, UTF-16 text frames); other types are library-only. A tag that fits the space the file already reserves is rewritten in place (FLAC gets a PADDING block to absorb slack; a 1–3 byte gap forces a rewrite), otherwise the file is rewritten to a temp file beside it and swapped in with `replaceItemAt`. Untouched fields, other frames and audio bytes are preserved. A successful write drops the override and refreshes the cached size/mtime so the next scan does not re-read it; a failure keeps the override and sets `writeReport`. Not supported: M4A (needs `moov` offset fixups), ID3 unsynchronisation, v2.2. The play queue still reads tags from the file when an item loads, so it can lag an edit.
- **Main window layout** (`MainView.swift`, `PlayerView.swift`). This is the original design (Now Playing stage, then Library / Lyrics / EQ cards) made responsive; an earlier two-widget in-window deck was removed at the user's request — do not bring it back. `MainView` reads the window size once (`GeometryReader`) and passes `width`/`isShort` to `PlayerBar` and `availableWidth` to `LibraryView`; views do not measure themselves. `PlayerBar` is three arrangements under `ViewThatFits` (wide ≥ 900 pt, medium ≥ 690, narrow). Cards: Library, `LyricsCard`, and `SpectrumView`/`BandControlsView`; with width ≥ `MainView.besideWidth` (1080) the lyrics sit beside the library (or the EQ when the library is off), else under. `Panels` (in `Controls.swift`) holds the saved switches (`library`, `lyrics`, `eq` = response/faders/none). `SpectrumView` and `BandControlsView` headers are `ViewThatFits` (one line, or two); `LibraryView` drops its middle column below 820 pt; `HeaderBar` sheds labels (`DeviceMenu(compact:)`). `PreampRow`, `BandCountPicker` live in `BandControlsView.swift`. `SpectrumView` and the visualizer window count the player as live (`player.state == .playing`) so they draw with the engine off.
- **Arrangement and Settings.** `Models/WindowLayout.swift` (pure, tested in `WindowLayoutTests`) owns the saved arrangement: card order, lyrics placement (`auto`/`left`/`right`/`stacked`), each card's size, and which card takes the spare height. `WindowLayout.arrange(...)` turns those plus the visible cards and the width into an `Arrangement`, and **both `MainView.cards` and the Settings preview draw from that one result** — change the rules there, not in a view. The defaults reproduce the original window exactly (lyrics beside the top card from 1080 pt, EQ stretches). `LibraryView(columnHeight:)`, `SpectrumView(graphHeight:)` (nil = flexible) and `BandControlsView(rowMaxHeight:)` take the sizes. `Views/SettingsView.swift` is the `Settings` scene (⌘,): Window Layout, Desktop Widgets, General. It is themed like the main window and writes the same `@AppStorage` keys / stores as everything else, so there is no Apply step. Its widget previews (`EQWidgetMock`, `NowPlayingWidgetMock`) are hand-drawn copies of the views in `ZuujisWidgets/` (the extension's views cannot be compiled into the app): **change a widget's layout and its mock together**. `ZMP_GALLERY_SETTINGS=1` with `-settingsPane layout|widgets|general` opens it for a screenshot (`settings-id.txt`).
- **Presets are applied in one place.** Every control (header menu, Equalizer menu, menu bar window, widgets) only sets `PresetManager.selectedPresetID`; the subscription made in `bootstrap()` (`presetLink`) applies it. It used to be `HeaderBar.onChange`, which meant a preset chosen from the menu bar window or a widget did nothing while the main window was closed. Do not add a second `applyPreset` beside a selection.
- **Speed.** `PlayerEngine.speed` (0.5…2×, `speedPresets`) and `keepsPitch` drive `AVAudioUnitTimePitch` (keeps pitch) or `AVAudioUnitVarispeed` (turntable), chained `player → varispeed → timePitch → EQ`; `applySpeed()` sets rate on one and bypasses the other, and both are bypassed at 1×. Measured, not assumed: the player node's `sampleTime` counts **source** frames at any rate, so `currentFrame()`, gapless `startSample`s and lyric sync need no rate correction. Do not add one. `NowPlaying` reports `speed` as the playback rate.
- **Loudness matching** (file player only; the system route cannot be matched per song). `Models/Loudness.swift` is pure: `LoudnessMeter` (ITU-R BS.1770 integrated loudness: K-weighting derived for any sample rate, 400 ms blocks every 100 ms, -70 LUFS and -10 LU gates; checked against ffmpeg's `ebur128` in `ReplayGainFileTests`), `ReplayGainInfo` (tag text to numbers) and `Loudness.gain(for:settings:)`, the one place a gain is chosen: the file's tags win over this app's measurement, the mode picks album or track and falls back to the other kind, an unknown song gets `fallbackDB`, and "keep peaks under full scale" caps a boost at `-20·log10(peak)`. Target is -18 LUFS (ReplayGain 2). `Models/ReplayGainTags.swift` reads the tags synchronously from the tag area only: FLAC comments (`FLACTags`), MP3 `TXXX` frames (`ID3Prefix.entries` now returns `REPLAYGAIN_*` user-text frames, nothing else from TXXX), M4A freeform atoms (`MP4Tags`, an atom walk of `moov › udta › meta › ilst`). `ViewModels/LoudnessStore.swift` (owned by `PlayerEngine` as `loudness`; its `objectWillChange` is forwarded through the player, so views observing the player see it) keeps tags and measurements in Application Support `loudness.json` keyed by path with size and mtime, **never writes to a music file**, measures the playing song, the next and the rest of the playing album in the background (`measureAhead`), and runs the Playback → Loudness Matching batches. Album gain for untagged albums is the length-weighted energy average of its songs' figures (`Loudness.albumLoudness`), and only for a song that has a figure itself. `URL` caches size and date: `loadEntry` clears that cache first, or a changed file looks unchanged. **The gain rides on `eqNode.globalGain` with the preamp** (`PlayerEngine.applyGlobalGain`; `player.volume` stops at 1 and is the sleep fade) and applies with the equalizer off too. A `Segment` carries its `gainDB` from the moment it is made, so a measurement arriving mid-song does not move the volume; the gain changes in `startSession` and at the gapless join in `segmentFinished`, and a settings change re-reads it at once (`refreshLoudnessGains`).
- **Limiter.** `Models/Limiter.swift` `SoftLimiter` is a look-ahead peak limiter (1.5 ms, ceiling 0.966, linked channels, allocation-free `process`, pure and tested in `LimiterTests`: the output never exceeds the ceiling and audio under it is bit-identical apart from the delay). It is the last stage of **both** paths and on by default (`AudioEngine.limiterEnabled`, key `limiterEnabled`). The file player runs it as a node after the EQ through `Audio/LimiterUnit.swift`, an in-process `AUAudioUnit` (`LimiterUnit.makeNode()`; node `bypass` is the off switch). The system route does **not** add a node to its graph: `SystemAudioRenderer.limit` calls `SoftLimiter` directly on the rendered buffer inside the IOProc, between the render and `write`, with a fresh limiter handed over in `setRenderTarget` on every graph build. Keep it that way: it leaves the tap, aggregate and graph lifecycle untouched. In `LimiterUnit` the input `AudioBufferList` pointer is fetched once (`AVAudioPCMBuffer.mutableAudioBufferList` rewrites the byte sizes from `frameLength` on every call, which made the upstream EQ fail with -50) and the buffers' own pointers are restored before each pull. Lyric sync adds the limiter's delay in `PlayerEngine.outputLatency`.
- **Clip light.** The preamp row shows `PeakLight` only while the limiter is on (amber LIMIT); with the limiter off it is hidden, because the user runs with it off and does not want a red CLIP lit through every loud song. Equalizer ▸ Limiter and Settings are the ways back on. Diagnostics still report clipping either way. `MeterSnapshot.peak` is the largest sample after the EQ and *before* the limiter, on both paths (the player's meter tap is on the EQ node; the route measures in `limit`). `MeterState.overDB` holds anything over full scale for two seconds, and `PeakLight` (in `BandControlsView.swift`, at the end of `PreampRow`) shows it: amber LIMIT with the limiter on, red CLIP with it off; clicking it toggles the limiter.
- **Sleep timer and resume.** `PlayerEngine.sleepTimer` (`off`/`until`/`endOfTrack`, never persisted; Playback → Sleep Timer). The timed one fades `player.volume` on the node (not the saved `volume`) and then pauses. `endOfTrack` works by *not pre-scheduling* the next track (`scheduleNext` and `reconcileWithQueue` both check it), so nothing of it is heard; `segmentFinished` then stops and puts the next song in the bar. `saveResumePoint()` runs on quit (`playerResumePoint`: path + seconds); `restoreCurrentTrack` loads it if it is the queue's current song, `currentTime()` reports it while stopped, and only `togglePlayPause` from stopped honours it (`playItem(resuming:)`) — every other `playItem` drops it, so a double-click always starts a song from the top.
- **Lyrics.** `Models/Lyrics.swift` is pure (LRC parse incl. multi-stamp, `[offset:]`, enhanced word stamps; plain text; `currentIndex(at:)` by binary search; tested in `LyricsTests`). `ViewModels/LyricsStore.swift` follows `player.$track` and reads, in order, a `.lrc`/`.txt` sidecar, a FLAC `LYRICS`/`UNSYNCEDLYRICS` comment, then AVFoundation's USLT / iTunes lyrics. The only network use is the opt-in LRCLIB lookup (`LyricsStore.fetchOnline`, off by default, `lyricsOnlineLookup`; sends title/artist/album/duration to lrclib.net, caches hits in Application Support `Lyrics/`). Keep it opt-in and never write beside the user's music (timed-lyrics output goes to the app's folder too). With the lookup on, untimed lyrics from the file still get looked up and LRCLIB's synced ones replace them; titles carrying the artist ("Song - Artist") are cleaned first (`withoutArtist`). Returning to the app re-checks for a `.lrc` that appeared beside the playing song (`recheckSidecar`). Saved lyrics start with `[zmp-length:N]` and `[zmp-meta:base64 JSON of Query]` so `recheckSaved()` can re-fetch without the song loaded; a cache line without them is untrusted. Selection: synced candidates within 8 s of the file's length, grouped by first-line time (±1 s) and line count; the group most entries agree on wins, then same album, then nearest length (LRCLIB has near-duplicates, mislabelled cuts and one-off outliers, so neither length nor an exact album match is trustworthy alone; "Circle In The Sand" was the case: an exact-length, exact-album entry was 23 s early). Bump `cacheRevision` when this changes; `/get` and `/search` both feed the candidates. **Time These Lyrics / Time Words** (button over lyrics without word times): `ViewModels/LyricsTimer.swift` runs macOS 26 `SpeechAnalyzer`/`SpeechTranscriber` on the song file (on-device; the model may download once), `Models/LyricsAligner.swift` (pure, tested in `LyricsAlignerTests`) aligns the heard words to the known lines by weighted LCS (a line starts at its first sung word, stepping back over misheard openers; unheard words are spread between neighbours) and writes enhanced LRC (`<mm:ss.xx>` per word) to the app's own `Application Support/Lyrics/Words/<hash of path>.lrc` (`LyricsTimer.wordsFile`), never the music folder; `LyricsStore.find` reads that copy before every other source. Line-timed lyrics ("Time Words") use `LyricsAligner.alignWords`: the whole song is aligned as for untimed lyrics and a line moves to where it is sung when its words were recognised within `maxShift` (6 s; LRCLIB had "The second hand unwinds" 5.4 s early) of its stated time plus the song's median offset; unrecognised and empty break lines keep the stated time plus that offset. Stated times (LRCLIB) are often 1-4 s off, so they are never trusted as-is (Quietdrive's "Time After Time" was the case). In `align`, a line's anchor is its first match that the next match follows within 1.5 s, step-back over unmatched words is capped at the words before the anchor, and fully missed openers back the start up ~0.32 s a word. **The song is listened to several times** (`LyricsTimer.listen` returns one word list per pass): the file as it is, its channels mixed to one, and that mix band-limited to 180 Hz – 5 kHz (`voiceCopies`, temporary files, deleted afterwards). The recognizer is a speech model and misses much of a vocal under a full stereo mix; the copies hear different words (on the Quietdrive song the plain file heard only "darkness has" of one line and one word of two "Time after time"s, all of which the mono copy heard). `LyricsAligner.align(lines:passes:)` matches each pass on its own (`match`), gives every line the pass that recognised most of its words, takes the opening from another pass when the best one missed it, and fills missed words from the others where they fit in order. A lyric-vocabulary `AnalysisContext` and `DictationTranscriber` were tried and did not help (dictation heard one line of the whole song). `Word.duration` is the recognizer's word length: one over 1.5 s has a silence counted into it, usually before the word, so a line never steps back onto it. Files carry `[zmp-words-rev:N]` (`LyricsTimer.wordsRevision`); older ones are ignored and redone by the next batch. Lyrics menu "Time Lyric Words for This Album / Whole Library" (`LyricsStore.timeWords`) runs that song by song (local lyrics, else LRCLIB if the lookup is on), skips songs already done so a stopped run resumes, and reports in `batchStatus`. `LyricLine.words` carries word times when a line has them, and the synced list lights the current line word by word. That list is `SyncedLyricsView` (`Views/LyricsLayerView.swift`), a layer view like those in `LiveViews.swift`: as SwiftUI rows it re-rendered the main window on every word and every frame of a line change (20-25% CPU with the card showing). It polls every 50 ms only while playing and on `timelineChanged`, touches layers only when the line or word changes, and animates a line change in one `CATransaction`. `LyricsBox` (`Views/LyricsView.swift`) keeps the plain-text and empty states in SwiftUI. **Every consumer must use `LyricsStore.time(for:)`** (position − `PlayerEngine.outputLatency` + the song's saved offset), never raw `currentTime()`: the node clock is render time, which runs ahead of what is heard. The widgets get line times pre-shifted by `outputLatency − offset` in `WidgetBridge.publish()`.
- **Desktop widgets** (`ZuujisWidgets/`, a second target: WidgetKit app extension `com.zuujis.MediaPlayer.Widgets`, embedded in `Contents/PlugIns`). There is no app group (no team; do not add one or commit an identity), so the app and the sandboxed extension exchange files in the app's Application Support folder, which the extension's entitlements open (`temporary-exception.files.home-relative-path.read-write`). `Models/WidgetState.swift` is compiled into both targets: the state JSON, the command file, `WidgetFiles`. `App/WidgetBridge.swift` (started from `bootstrap()`) writes `widget-state.json` + a 320 px `widget-art.jpg` on changes, debounced 0.6 s, then `WidgetCenter.reloadAllTimelines()`; it also watches `widget-commands/` (DispatchSource) and runs the buttons' commands. Widgets never tick: progress is `ProgressView(timerInterval:)` and the lyric line changes through timeline entries pre-scheduled at each line's start (`position + (now - anchor) * speed`), so any change to position, speed or pause state must go through `publish()`. Buttons are `AppIntent`s in the extension that only write a command file (`WidgetCommand`: name, arg, amount, `sent`); the bridge runs them oldest first, republishes at once (no debounce wait), ignores any older than 20 s and discards whatever is waiting at launch. `publish()` skips the write and reload when nothing a widget shows has changed. `WidgetSettings` (in `WidgetState.swift`, edited in Settings, kept by `ViewModels/WidgetSettingsStore.swift` in preferences) travels inside the state file: which presets the Equalizer widget offers and in what order (`state.presets` is already resolved), what each size shows, columns, button size, dB step; and the Now Playing options. New fields in `WidgetState` must be Optional and new `WidgetSettings` fields need a line in its tolerant `init(from:)`, because the app and a still-running old widget process read each other's files. The cover file is removed when a song has none. The Equalizer widget deliberately has no faders or graph: a widget cannot be dragged, so it is a tap remote (power, bypass, preset buttons, 1 dB bass/mid/treble/preamp steppers via `nudgeTone`/`stepPreamp`, flat). Do not add a display that looks draggable. Desktop widgets are drawn flattened ("accented") unless the user sets Widget style to Full-color; use `widgetAccentable` and shape/opacity, not colour alone. After installing, `killall ZuujisWidgets chronod` or macOS keeps running the old widget code. Widget code cannot use the app's `Theme`; `WTheme` copies Midnight. New widget files are registered in the target's own Sources phase (`addsource.py` only knows the app target); shared files need a second PBXBuildFile. The installed copy's re-sign step (`codesign --deep`) also re-signs the appex.
- **Menu bar item and login.** `MenuBarExtra` (`.window` style) in `ZuujisMediaPlayerApp.swift` shows `MenuBarPlayer` (`Views/MenuBarPlayer.swift`) with the same environment objects as the main window. `bootstrap()` (attach player, lyrics, open handler, saves, device profile) runs from the main window's `.task` **and** the menu bar icon's `.task`, so it must stay idempotent: a login launch has no window. `App/LaunchAtLogin.swift` wraps `SMAppService.mainApp`; `enableOnFirstRun()` registers once, only from `/Applications` or `~/Applications`, so a DerivedData build never registers itself. `AppDelegate` hides the app when the launch Apple event carries `keyAELaunchedAsLogInItem` and returns false from `applicationShouldTerminateAfterLastWindowClosed` (the menu bar item keeps it alive; ⌘Q quits). The main `WindowGroup` has id `main` so the menu bar can reopen it.
- `ZuujisMediaPlayer/Audio/NowPlaying.swift` publishes the current track to `MPNowPlayingInfoCenter` and routes `MPRemoteCommandCenter` (play, pause, toggle, next, previous, ±10 s, scrub) to the player; that is also what makes the keyboard's media keys control this app instead of launching Music. It refreshes on state/track change and on `PlayerEngine.timelineChanged` (seeks, joins) — the system extrapolates elapsed time from the playback rate, so there is no per-second update.
- While a file plays, the player taps the EQ's output and feeds `MeterState` and, through `AudioEngine.externalVisualizerFrame`, the visualizer; both are cleared on pause/stop so silence still reads as silence. This is lossless *decoding* but not yet bit-perfect *output*: unless the device rate is matched. `OutputRate` (Audio/OutputRate.swift) sets the default output's nominal rate to the file's own rate (or its lowest supported integer multiple) in `PlayerEngine.buildGraph`, before the new engine exists, and `finish()` restores the old rate. It is skipped while the system route is running — changing the rate under its tap/aggregate would silence it — and the old engine's config-change observer is removed first so the change does not trigger a rebuild. The header toggle is `matchSampleRate`. `exclusiveMode` (off by default) takes the device's hog mode in the same place, held in `hogged`, released in `finish()`, when switched off, and whenever the system route starts (`equalizer.$isRunning`); the OS frees it if the process dies. It only takes effect when a graph is built, not mid-track. Untested on real multi-rate hardware.
- `ZuujisMediaPlayer/Models/`: `EQBand`, built-in `EQPreset` definitions and frequency layouts, plus `AudioDevice`.
- `ZuujisMediaPlayer/Models/DeviceProfile.swift` and `ZuujisMediaPlayer/ViewModels/DeviceProfileStore.swift`: per-output-device EQ profiles, persisted to `deviceProfiles.json` beside the presets. Keyed by Core Audio device UID, never by name — names are not unique and change, the UID survives reconnects. The stored name exists only so absent devices can still be listed.
- `ZuujisMediaPlayer/ViewModels/PresetManager.swift`: custom preset CRUD and JSON import/export. Persistent presets live in the user's Application Support `ZuujisMediaPlayer/presets.json`, never in the repository.
- `ZuujisMediaPlayer/Views/VisualizerView.swift`: the Visualizer window — a Metal renderer with some fifty modes in five families. Geometric and particle modes build vertices on the CPU each frame; shader modes are full-screen fragment programs and use no CPU geometry at all. All shaders live in `VisualizerShaders.swift` as one source string compiled at runtime, so there is no `.metal` file to register and no dependency.
- **Immersive family** (`Views/ImmersiveRenderer.swift`, `Views/ImmersiveShaders.swift`): the scenes the shuffle plays by default, added because the older modes read as flat. `VisualizerMode.immersive` maps a mode to an `ImmersiveKind`; `VisualizerRenderer.encode` calls `ImmersiveRenderer.update` before its scene pass (compute kernels and offscreen passes) and `draw` inside it, then runs the usual mips and composite. Three techniques: **particles** (Murmuration, Singularity, Attractor: 2^20 particles stepped by `k_particles`, then projected and summed into a fixed-point `UInt32` grid with atomic adds by `k_splat`; point sprites were measured at three times the cost, and the grid is capped at 1080 rows so a 4K window costs the same; depth of field is a fixed random offset per particle), **fluid** (Liquid Light, Plume: stable fluids in compute kernels, velocity at 288 rows and dye at 720), and **offscreen fragment scenes** (Deep Field: the view from a ship at speed. Twenty-four star sheets at different depths come toward the camera and wrap, each pixel looking along a short stretch of depth so speed draws the stars into streaks; **the stars alone carry the speed**. Galaxies are Hubble photographs from the `DeepFieldGalaxies` data set in the asset catalog, a 6 by 4 sheet of 640-pixel tiles each faded to black at the rim so it can be added over the sky, and they stay small and take minutes to drift, because flying through them read as wrong; the far sky is the `DeepFieldSky` deep-field photograph. Sources are listed in `docs/deep-field-credits.md`; keep that file in step if a photo changes. Cathedral: a raymarched Apollonian lattice with a corridor bored through it so the camera always has clear air, lit by a lamp that flies ahead of the camera), rendered at `ImmersiveKind.maxRows` and scaled up. Measured on this Mac at 3840x2160: 6-13 ms a frame. Rules: colour is linear light (`pal` returns squared values) and the composite applies ACES and gamma when `Uniforms.filmic` is set; for these presets `paletteShift` means palette (whole part picks one of four gradients, fraction slides along it) and `seed` moves the camera or picks the attractor; every motion integrates `u.dt` (the audio clock's step, zero in silence) or reads `u.time`/`u.travel`, never a frame counter; the feedback pass does a plain decay for them, because `capped` and the hue bleed mix channels and let a bright pixel flicker between two half-float values forever in silence. Metal needs `thread` on reference parameters. `SU` and `SceneUniforms` must stay in step (twenty floats). The fluid is drawn by its folds (`f_fluid` lights the gradient of the dye and leaves the body a thin veil): filled dye read as flat paint with hard edges. **Judge these scenes moving, with real music**: build Debug and run the binary with `ZUUJIS_DATA_DIR=<empty folder> ZMP_GALLERY=<out> ZMP_GALLERY_UI_ONLY=1 ZMP_GALLERY_VISUALIZER=1 ZMP_GALLERY_HOLD=1 ZMP_GALLERY_SCREEN=left ZMP_GALLERY_MUTE=1 ZMP_GALLERY_PLAY=<a real song>` and `-visualizerMode "Deep Field"`, then `screencapture -o -x -l $(cat <out>/visualizer-id.txt)` every few seconds (that captures only the Visualizer window) and kill the app. The synthetic gallery signal hides most of what is wrong. For a close look, `ZMP_GALLERY_ONLY=Cathedral,Plume ZMP_GALLERY_TILE=1280x720` with `ZMP_GALLERY` renders just those presets, saves three moments of each as PNG and reports GPU ms per frame.
- **Shuffle** plays `VisualizerPreset.immersiveRotation` only. "Include classic presets" (`visualizerClassicInShuffle`, off by default) adds `rotation` and `remix()`; "Include MilkDrop presets" (`visualizerShuffleMilkdrop`) is now off by default too. Both are in the Visualizer window's timer menu.
- Shader modes are one `m_<name>` function each, dispatched by `u.mode` in `f_procedural`. Adding one means a function, a `case` in that switch, a `VisualizerMode` case and its `proceduralIndex`; it then appears in the menus and the shuffle by itself. They read three audio sources: the 64-bin spectrum (`bandAt`), the 256-sample waveform (`waveAt`), and a 64x128 history texture (`histAt`) holding the last couple of seconds of spectra, which is what the ridgelines, the skyline and the polar spectrogram draw.
- The accumulation textures are `rgba16Float` with a mip chain. Float, because 8-bit trails stall a few levels above black under a slow decay; mips, because the composite pass reads them as bloom. `capped()` in the feedback pass limits a trail by scaling the whole colour, not each channel — a per-channel clamp is what turned additive modes white. Point sprites are sized in pixels, so they are scaled by drawable height (`pointScale`).
- The renderer ping-pongs between two offscreen textures. Each frame the previous one is re-sampled through a zoom/rotate/drift/ripple transform and dimmed (`f_feedback`), this frame's content is drawn over it, and a final pass tone-maps the result onto the drawable. That warped feedback — not the geometry — is what produces the tunnels, spirals and marbling; it is the technique MilkDrop and G-Force are built on, and a plain fade to black does not achieve it. Two textures are required because a pass cannot sample the target it draws into.
- Modes come in five families. Geometric and particle modes are bespoke builders; shader modes are full-screen fragment programs; **replicator** and **simulation** modes are compositional, following Apple Motion's model. A `ReplicatorSpec` is a cell (what to draw) plus a layout (where to place copies: burst, spiral, wave, grid, scatter, ring) plus a sequence offset — Motion's Sequence Replicator — so a wave of change travels across elements instead of all of them pulsing together; element *N* takes spectrum bin *N*. A `ForceField` is Motion's simulation behaviors (vortex, orbit, attractor, repel, gravity, wind, drag, random motion) integrated per particle, attached to the emitter rather than to each particle. Prefer adding a spec over writing another bespoke `buildX()`: the compositional axes multiply, the bespoke ones do not.
- `ZuujisMediaPlayer/Audio/MilkdropPreset.swift` reads `.milk` presets: a parser and evaluator for MilkDrop's per-frame language, plus per-pixel evaluation. Three things this cost time to learn. **The static header is not the preset** — across the original pack `rot`/`dx`/`dy`/`cx`/`cy`/`sx`/`sy` are all at defaults, so importing header values alone yields motionless, indistinguishable presets. **The motion is per-pixel**, not per-frame: `zoom` and `rot` are assigned in `per_pixel_*`, which means the transform varies across the screen and a single global transform cannot express it — hence the warp mesh. **Built-in motion variables reset to their header values every frame**; only user variables and `q1`-`q32` persist. Without that reset, `zoom = zoom - 0.05` compounds and the preset destroys itself in seconds.
- The warp mesh is a 33x25 grid whose vertices stay put while their texture coordinates move. Evaluating the per-pixel equations at every vertex costs about 3.5 ms per frame, roughly a fifth of the 60 fps budget — measured, not assumed, before the renderer was built around it. Imported presets are faithful in *motion* only: `per_pixel` colour work, custom waves and shapes, and MilkDrop 2's HLSL blocks are all ignored.
- Preset files live in Application Support, never in the repo or the bundle: the packs are community works with unclear licensing, so they are something the user brings.
- A `VisualizerPreset` is a mode plus its feedback transform, which is where the variety comes from: the same geometry looks entirely different tunnelled, spiralled or smeared. `Auto` is a shuffle: a bag of the hand-tuned `VisualizerPreset.rotation` (none repeats until all have played), interleaved with `VisualizerPreset.remix()` — a random mode under a random feedback transform and palette — and, if any are imported, MilkDrop presets. Each is held for the user's dwell (`visualizerDwell`, 30 s by default, counted in audio time) and then switched on a detected beat. A switch clears nothing: the old picture stays in the feedback buffer and the new content's alpha ramps up (`fade`), so presets dissolve into each other. Two struct layouts must stay in step with the shader: `VisualizerVertex` against `VIn` (float2 at 0, float4 at 16, float at 32, 48-byte stride) and `VisualizerUniforms` against `Uniforms` (twenty floats then an int at offset 80, 84-byte stride).

## Audio path and lifecycle

When the user presses Start, `AudioEngine`:

1. Gets the current default output device.
2. Creates a private system process tap that excludes this app and uses `.mutedWhenTapped`.
3. Creates a private aggregate device combining that tap with the physical output.
4. Runs an `AudioDeviceIOProc` on the aggregate. Its realtime callback sends captured frames through an `AVAudioEngine` in manual-rendering mode, where `AVAudioUnitEQ` applies the bands and global gain, then writes the rendered frames to the real output buffers.
5. Samples a lock-protected 1,024-frame rendered-audio ring buffer at 20 Hz for the UI meters and spectrum.

The output-device listener updates `selectedOutputDeviceID`; while running, the app tears the route down and rebuilds it from scratch. Do not reintroduce an in-place `setComposition` switch — see the tap-lifetime rule below.

## Critical audio safety rules

- The tap **must not be created at launch**. A live tap mutes the audio it captures; create it only in `start()`.
- **Stopping the aggregate's IOProc permanently deactivates its auto-started tap.** A new IOProc on the same aggregate starts cleanly and reports no error, but the capture buffers stay zeroed while the tap keeps muting the real output — the device just goes silent. Anything that needs to change the graph while running (a band-count change, a preset with a different band count) must call `teardownRenderGraph()`/`buildRenderGraph()` and leave `ioProcID` alone. Only a full stop may call `stopIOProc()`. This is what "changing the band count mutes it" was.
- **The tap is not always buffer 0 of the IOProc's input list.** An aggregate lists each sub-device's own input buffers before the tap's, so an output device that also captures — the Xbox headset bridge publishes a microphone alongside its output — shifts the tap along. `tapBufferOffset(tapChannels:)` computes the offset and `SystemAudioRenderer.inputBufferOffset` applies it. Reading buffer 0 unconditionally feeds the EQ that microphone instead of the system audio, which sounds exactly like the device has been muted.
- Each processing session builds a **fresh `AVAudioEngine`**. Repeatedly enabling and disabling manual rendering mode on one instance leaves the graph alive but rendering silence.
- Always destroy both the aggregate device and process tap on every stopped/error path. `teardownSystemAudioRoute()` is what restores normal system audio.
- Exclude this app from the tap by both process object (when available) and bundle ID. Removing that exclusion can create self-capture/feedback or silence output.
- Keep `AudioEngine` main-actor isolated. `SystemAudioRenderer` deliberately owns data touched by the IOProc and is `@unchecked Sendable`; do not access SwiftUI/`@Published` state from that callback.
- The IOProc and source-node callbacks are realtime paths: no allocations, logging, I/O, actor hops, or locks that may block. The renderer's meter capture only uses `try()` on its lock; metering is best-effort.
- Do not assume a particular channel layout. The renderer handles interleaved and non-interleaved Float PCM and maps/repeats source channels as needed.
- If modifying stop/rebuild logic, verify the engine stops, route resources are destroyed, and audio returns after an error or output-device switch.

## State and UI conventions

- `bands` is the source of truth. Call `applyBandToNode(_:)` after a single-band mutation or `applyAllBands()` after a batch mutation.
- Changing band count replaces the EQ node because `AVAudioUnitEQ` has a fixed band count. Preserve nearest old-band settings, as `setBandCount(_:)` does.
- Gain is clamped to `-24...24 dB`; bandwidth is clamped to `0.1...5.0`; master gain is a multiplier limited to `15.85` (about `+24 dB`) and applied through `AVAudioUnitEQ.globalGain`.
- `isBypassed` changes each EQ filter's bypass state; it does not tear down the system route. `toggleBypass()` is the header's Bypass button and ⌘B.
- Meter updates belong on `MeterState`, not `AudioEngine`, to avoid invalidating all slider views ~20 times per second. For the same reason the live level drawn behind the faders is one separate view, `BandLevelBackdrop` (one layer view laid behind the band row), not something each `BandSlider` observes.
- **Anything in the main window that moves during playback is drawn with Core Animation layers in a plain `NSView`, never with SwiftUI** (`Views/LiveViews.swift`: `StageSpectrum`, `BandLevelBackdrop`, `ResponseSpectrum`, `LiveLevelMeter`, `LatencyChip`, `Scrubber`; the synced lyrics list in `Views/LyricsLayerView.swift`). Measured: a SwiftUI view that redraws inside the main window re-lays out the whole window on each frame (about 17 ms), and putting it in its own `NSHostingView` does not help, because a hosting view marks its ancestors as needing a constraints pass on every update. The spectrum and scrubber alone held playback at 34% CPU with every card hidden; as layer views it is about 5%. `LiveMeterView` is the base class: a 30 Hz timer that runs only while audio is live and the window is visible, reading `MeterState.snapshot` directly instead of observing it. Do not add a `TimelineView`, a repeating timer that sets `@State`, or a meter-observing SwiftUI view to the main window; check with `top -l 5 -s 2 -pid <pid> -stats cpu` and `sample <pid> 5` while a song plays.
- **Pointer movement is thinned** by `App/PointerThrottle.swift` (a local `.mouseMoved` monitor installed in `applicationDidFinishLaunching`): SwiftUI hit-tests the whole main window on every mouse-moved event to serve `onHover`, about 2.5 ms a time, which was 10-15% CPU while the pointer moved. One event per 0.1 s passes while it moves and the resting position is delivered 40 ms after it stops. Clicks, drags and scrolling are not filtered. Measure with a fast scripted pointer sweep (the user moves the pointer quickly), not by hand. **Keep decorative views out of hit-testing** (`.allowsHitTesting(false)`), above all `NSViewRepresentable`s: the 31 faders' drawing and their `ScrollWheelReader` views more than doubled the cost of every hover check; `VerticalGainSlider` now takes its gestures on one clear overlay. `ClipLevel` publishes only `isOver`: `overDB` changed several times a second with a hot preamp and each change re-laid out the window.
- The main window's content fills its height (see Widgets above): the graph and the band row are the flexible pieces of the EQ widget (the row is capped at 360 pt; the fader track length is whatever is left after `BandSlider.labelsHeight`). The minimum window is `MainView.minSize` (620 × 460). Check layout changes at 1240×1000 (lyrics beside the library), 900×900, 640×900 and 760×560, with the library and lyrics on and off.
- **Everything the visualizer draws must be driven by audio.** One clock (`phase`) feeds every time-based motion — shader patterns, replicator spin, the sequence wave, the feedback ripple — and it advances in proportion to audio energy, so silence freezes the whole renderer. Do not reintroduce a wall-clock increment, and do not give an element a non-zero size or emission rate at zero signal; a visual that animates in silence is decoration. The one wall-clock term is the ~1 s `fade` of a transition, which runs once and stops. Verify both directions: with the engine stopped, successive captures of the window must be byte-identical, and with audio they must differ.
- **Library lists are windowed.** `WindowedRows` (`Views/LibraryView.swift`) is the scrolling list for artists, albums, genres, songs and playlist songs: rows of one fixed height, of which only those in view plus a small margin exist (spacers stand in for the rest; `WindowedRowsMath.window`). Do not go back to `LazyVStack` (it keeps every row it has shown: 45 MB after scrolling 1,000 songs, because a row with its context menu is 30-100 KB) or to `List` (it built every row at launch: +110 MB). A row's height must be the one passed to `WindowedRows` (`row(height:)`, `songRowHeight`); rows are identified by index. Numbers: [docs/cpu-notes.md](docs/cpu-notes.md).
- **The main window's place is kept by `App/WindowPlacement.swift`**, not by SwiftUI: SwiftUI restores the size but opens the window on the display that has keyboard focus, shifting the saved position onto it. The frame is saved under `mainWindowFrame` on every move, resize and close, and put back when a main window first becomes visible, if a screen still covers that place. Only windows already put back are recorded, so the misplaced starting frame is never saved.
- **The EQ filter is the app's own.** `Models/BiquadEQ.swift` (pure, tested in `BiquadEQTests`) is the biquad cascade plus the preamp gain; `Audio/EQUnit.swift` wraps it as an in-process `AUAudioUnit` (`GraphicEQ` is the handle the engines hold: `node`, `set(bands:bypassed:)`, `globalGain`). Both paths put that node where `AVAudioUnitEQ` used to be, so the graphs and the tap lifecycle are unchanged. It takes its sections from `EQResponse.section`, always one per band (identity when off or at 0 dB), glides to new coefficients over a few milliseconds, and takes any band count, so nothing rebuilds a graph when the count changes (`rebuildEQNode` is gone). Keep it in double precision (single leaves the low bands' error 46-66 dB under the signal) and keep the staggered order in `cascade` (section *k* on sample *t − k*): that order is the whole speed-up, and it is bit-identical to `vDSP_biquadmD`. All-identity (flat, bypassed) skips the filter after 1 s.
- **Silence is not rendered.** `SystemAudioRenderer.process` skips the EQ graph once the tap has delivered 2 s of exact zeros (`silentFrames`, `idle`) and writes zeros to the device; it renders again on the first non-zero cycle. While idle `copyLatestFrames()` returns nil and the meter timer calls `MeterState.routeSilent`, which also hands the meters back after the player stops. Keep the hold longer than the filters' and limiter's ring-out. `PlayerEngine.restEngineSoon()` pauses the player's engine 3 s after a pause; `resume()` then restarts from `pausedFrame` through `startSession`. `LiveMeterView` stops touching layers after 5 s without signal (`restsOnSilence`). The clip light goes out only after a full hold with no peak, and has no fade: an animated SwiftUI change renders the whole window on every frame. History and numbers: [docs/cpu-notes.md](docs/cpu-notes.md), which is also where CPU findings are logged from now on.
- `SystemAudioRenderer.clearAnalysisBuffer()` must be called whenever processing stops. `scratchFilled` latches true, so without it the ring keeps serving its last frames and meters and visuals animate from a frozen snapshot long after the engine has stopped.
- `visualizerFrame()` is pulled at display rate, not the 20 Hz meter rate. Its `bass` and `level` come from the newest 512 samples through a ~150 Hz one-pole filter rather than the 2,048-sample FFT window: that window is tuned for frequency resolution and smears the transients a beat-reactive visual has to land on.
- `master gain` persists to `UserDefaults`; band curves do not. `init()` assigns the backing store directly, because the `didSet` would write straight back and `eqNode` does not exist yet.
- **Menu bar** (`ZuujisMediaPlayerApp.swift`): app menu (About, Make Default Audio Player…, Open at Login), File (open, add to queue, library folders), View (Lyrics ⌥⌘L, panel switches ⌘L/⌘G/⌘E, Show Queue, Open Visualizer, Theme — added to the system View menu with `CommandGroup(before: .toolbar)`, so Enter Full Screen stays), Playback (incl. - **Default player and the old name.** `DefaultPlayer.makeDefault()` registers this bundle with Launch Services. macOS names the app in its confirmation by bundle ID, so any *other* registered copy with the same ID (an old build in a temp folder, the pre-rename `AudioEqualizer.app`) can lend its name: that was "Audio Equalizer still shows". Check with `lsregister -dump | grep -B3 -A3 com.zuujis`, and unregister stale copies with `lsregister -u <path>`. Unregister and delete test builds when done.
- Device profiles capture on a 1.2 s debounce and apply from `selectedOutputDeviceID.didSet`, which flushes any pending capture against the *outgoing* device first: the timer would otherwise fire after the switch, when `bands` already belongs to the new device, and the last edit before a switch would be lost. `isApplyingProfile` guards the capture/apply loop, since applying mutates `bands` and `masterGain`. A profile saved at a different band count applies via `rebuildEQNode()` — the same teardown/build path as `setBandCount`, never `stopIOProc`.
- Built-in presets are `EQCurve`s — control points interpolated on a log-frequency axis — not fixed band lists. `applyPreset` resamples the curve onto the current layout, so selecting a preset in 31-band mode keeps 31 bands. Custom and imported presets have `curve == nil` and still set the band list (and therefore the layout).
- **A band's `gain` is what the user wants to hear at that frequency, not what the EQ unit is given.** Neighbouring bands overlap and their gains add — at one octave everywhere a +4.5 dB preset delivered +15 dB on 31 bands — so `EQResponse.compensated` solves for the unit gains that make the summed response equal each band's gain at its own frequency. `syncEQNode` and `applyBandToNode` both go through it, and the graph draws the same compensated sections, so the curve passes through the handles. Never write `bands[i].gain` straight to `eqNode`. Because one fader changes its neighbours' unit gains, `applyBandToNode` refreshes every gain.
- **Band width follows the layout** (`EQPreset.bandwidth(forBandCount:)`): 1.6 octaves on 10 bands, 1.0 on 15, 0.5 on 31 — about 1.5 times the band spacing. With the overlap compensated, width is chosen for smoothness: those values leave under 0.4 dB of ripple across a flat setting, where a width equal to the spacing leaves 2 dB. `setBandCount` assigns it and `EQPreset.withLayoutBandwidth` brings saved profiles and custom presets up to date. The parametric biquad model in `EQResponse` matched `AVAudioUnitEQ`, which filtered before `BiquadEQ`, to 0.01 dB (checked by rendering an impulse through the unit offline — and note that a manual-rendering engine must be given an explicit format, or it renders at the mixer's 44.1 kHz and every measured frequency is 9% off).
- Preset curves are written to be roughly tone-neutral in level. A preset that lifts every band is a volume control, and on top of the master gain it only buys clipping.
- Built-in presets are recreated in memory. Only custom presets are persisted. Imported JSON must decode as a single `EQPreset`.
- `BandControlsView.bandRow` sizes band columns to the available width and only falls back to horizontal scrolling once even `minColumnWidth` no longer fits. A SwiftUI `Slider` is always horizontal: it is laid out at full track length and then rotated, so the outer frame must be the transposed size or every band reserves a track-length of horizontal space.

## Validation checklist

- Run `swift test` in `Tests/` after touching the EQ maths, `Loudness`, `Limiter`, `ReplayGainTags`, `LoudnessStore`, `Lyrics`, `PlaybackQueue`, `OutputRate`, `LibraryModel`, `LibraryStore`, `Playlist`, `PlaylistStore`, `AppPaths` or `TagWriter`. It is a package that symlinks those files from `ZuujisMediaPlayer/` (nothing is duplicated and the Xcode project is untouched), so a file under test must import only Foundation, AVFoundation or CoreAudio. A new file under test needs a symlink in `Tests/Sources/ZuujisCore/`. `TagWriterTests` build real FLAC/MP3 files with ffmpeg and check them with ffprobe/metaflac/flac (skipped if absent); `LibraryStoreTests.testRealFolder` is opt-in via `Zuujis Media Player_REAL_LIBRARY`. Queue tests persist to a temp folder, never Application Support. The audio path and UI are not covered: test those by hand as below.
- Build the `ZuujisMediaPlayer` scheme after Swift or project-setting changes.
- Manually test audio changes on a machine that supports process taps: Start, play system audio, alter a band and master gain, Stop, then confirm ordinary system audio still plays.
- Change the macOS default output while running and verify the app follows it. Test a route-creation failure or Stop after Start to ensure no tap/aggregate is left behind.
- For UI work, check 10-, 15-, and 31-band modes plus the horizontal slider scroll layout.
- Switching band count and applying presets **while running** is the regression-prone path: verify audio keeps playing without toggling the engine off and on.
- Test against a virtual output device that also has an input stream (the Xbox headset bridge) — that is the case the tap-offset logic exists for.
- The full manual pass for the audio route (start/stop, changes while running, output switches, permission states, sleep) is [docs/audio-route-checklist.md](docs/audio-route-checklist.md). Run it after changes to `AudioEngine`, the renderer, device switching or profiles.
- Saved JSON (library, queue, playlists, device profiles, custom presets) goes through `SavedFile`: each save keeps `<name>.bak`, an unreadable file is moved to `<name>.corrupt-<date>.json` and the backup restored, and problems show via `DataIssues` in the header. Do not write those files with a bare `try? data.write`.

## Repository hygiene

- Keep source under the existing app folders and do not commit Xcode user-state or DerivedData files.
- The project is `objectVersion 56` with no file-system-synchronized groups, so a new source file must be hand-registered in `project.pbxproj` in four places: `PBXBuildFile`, `PBXFileReference`, the owning `PBXGroup`'s children, and the target's `PBXSourcesBuildPhase`. Verify with `plutil -lint` afterwards.
- Preserve the existing SwiftUI style and inline comments; comments around Core Audio lifecycle code document real safety constraints.
- `README.md` holds the user-facing setup and usage guide; keep this file focused on implementation context. The project is GPL-3.0 (`LICENSE`).
- Signing is "Sign to Run Locally" (`CODE_SIGN_IDENTITY = "-"`, no team) so anyone can build it. Do not commit a personal signing identity or team ID: the repository is public.
- `python3 Tools/addsource.py <sibling.swift> <Group/New.swift> …` does the four-place `project.pbxproj` registration for new files (the sibling is any file already in the same group); still run `plutil -lint` after.
